# 第三方卡面 / 谱面导入调研

> 结论（2026-10-22 修订）：
> **谱面可行且成本低** —— 谱面由服务端下发，只需放 JSON + 补两行主数据。
> **卡面也已落地且成本低** —— 卡面纹理在服务端资源包里，不在 APK 内；
> 换图 = 改写资源包条目或直推客户端，**不重打 APK、不重签名**。
> 两者的格式都已在真实样本上逐字节验证（不是推测）。

---

## 一、谱面（beatmap）

### 1.1 现状：谱面在服务端，不在客户端包里

这是本次调研最重要的一条修正 —— 之前以为谱面要走 `/download/getUrl` 拉 `extracted/`，实际上：

| 事实 | 证据 |
|---|---|
| 谱面文件在服务端 `assets/serverdata/beatmaps/` | 已有 **1912 个** `Live_*.json`，共 61.7 MB |
| 游戏内加载走接口，不走静态下载 | [live.go:97](../internal/handler/live/live.go#L97) `loadLiveNotes()` 直接读该目录并塞进 API 响应 |
| 没有谱面的曲子会被过滤掉 | [common.go:114](../internal/handler/api/live/common.go#L114) `hasBeatmap()` 用 `os.Stat` 判断 |
| 主数据通过文件名关联 | `live_setting_m.notes_setting_asset = 'Live_0001.json'` |

所以**换谱面 = 换个 JSON 文件**，不需要动客户端、不需要重签 APK。

### 1.2 谱面格式（已在真实文件上验证）

顶层是一个扁平数组，每个元素是一颗音符：

```json
[
  {"timing_sec": 6.664, "notes_attribute": 1, "notes_level": 1,
   "effect": 3, "effect_value": 2.286, "position": 5},
  {"timing_sec": 10.664, "notes_attribute": 1, "notes_level": 1,
   "effect": 1, "effect_value": 2, "position": 7}
]
```

字段语义（统计自 200 个真实谱面、共 5.2 万颗音符）：

| 字段 | 取值 | 语义 |
|---|---|---|
| `timing_sec` | float，秒 | 音符判定时间点 |
| `position` | **1..9** | 判定线位置（左 1 → 右 9） |
| `notes_attribute` | 1 / 2 / 3 | 属性：Smile / Pure / Cool（决定音符颜色） |
| `notes_level` | int | 音符等级（影响图标大小/外观） |
| `effect` | 1 / 2 / 3 / 4 | 音符类型，见下 |
| `effect_value` | float | `effect=3` 时是**长条持续时长（秒）**；其余类型恒为 2..4 的枚举值 |

`effect` 观察到的分布与时长特征：

| effect | 出现次数 | effect_value 特征 | 推断 |
|---|---|---|---|
| 1 | 38019 | 全是 2 / 3 / 4（6 种） | 普通点击音 |
| 2 | 2750 | 2..4（5 种） | 长条**起点** |
| 3 | 5567 | **394 种**，0.17..9.0 秒连续值 | 长条**终点**，值=持续时长 |
| 4 | 6110 | 仅 1 / 2 / 4 | 同步/双押或滑动类音 |

> `effect_value` 在 effect≠3 时不是时间，而是离散枚举 —— 移植时**不要**把它当时间戳用。

### 1.3 加一首新曲的最小步骤

1. 放谱面：`assets/serverdata/beatmaps/Live_9001.json`（自己造的编号，别和现有冲突）
2. 插 `live_setting_m`：`notes_setting_asset='Live_9001.json'`，同时给
   `live_track_id`（曲子 ID）、`difficulty`、`stage_level`、四档分数线
   （`c/b/a/s_rank_score`）、`c/b/a/s_rank_combo`、`live_icon_asset`（封面图路径）
3. 插 `normal_live_m`：`live_difficulty_id` + `live_setting_id` + `default_unlocked_flag=1`
4. 重启服务端 → 客户端「乐曲」列表出现新曲

**卡点**：`live_icon_asset` 指向客户端里的封面图（`l_jacket_XXX.png` → 实际是 `.texb`），
新曲若想有独立封面必须走第二节的纹理改包；复用现有封面则可以完全不动客户端。

**另一个卡点**：曲子音频在客户端 `assets/sound/live/*.ogg`，服务端不下发音频。
自造曲想有声音，需要把 ogg 也塞进客户端资源（同第二节流程）。

### 1.4 从 llpractice 移植的可行性

结论：**技术上可行，主要工作量在数据映射与判定参数标定**。

可直接映射：

| llpractice | 本项目 |
|---|---|
| 音符时间 | `timing_sec` |
| 轨道（假设 9 轨） | `position` 1..9 |
| 长条 | 起点 `effect=2` + 终点 `effect=3`，`effect_value`=终点−起点 |
| 点击 | `effect=1` |

必须自己算的东西：

1. **分数线**：`c/b/a/s_rank_score` 与 `*_combo` 原本是按官方谱面难度调的，
   自造谱要按总音符数重算（否则 S 分永远拿不到 / 一碰就 S）。
   可以先按 `音符数 × 单音符基础分 × 连击系数` 估，再真机标定。
2. **`notes_attribute`**：官方谱按小节切换属性色，自造谱可以全填 1。
3. **`effect=4` 的语义未完全确认**，移植时先只产出 1/2/3 三种，避免误判。
4. **曲长与节奏对齐**：`timing_sec` 是绝对秒，需要和音频文件的起始静音对齐，
   否则整谱偏移。建议先拿一首官方谱 + 官方 ogg 做一次「解码 → 重编码 → 对拍」验证。

风险等级：**低**（纯数据，随时可回滚）。

## 二、卡面（card art）

### 2.1 资源分层

一张卡的立绘在客户端里是**两层**：

| 层 | 文件 | 说明 |
|---|---|---|
| 占位 | `assets/image/units/u_normal_icon_11011001.png.imag` | 只有 **74 字节**，不是真图，是给资源的引用壳 |
| 实体 | `assets/image/units/tx_u_normal_icon_11011001.texb` | 真正的纹理容器（样本 6793 字节） |

`unit_m` 表里的 `normal_icon_asset` / `rank_max_icon_asset` 写的是 `.png` 路径，
客户端据此推导出同名的 `tx_*.texb` 去加载。签名卡另有 `unit_sign_asset_m` 指向
`assets/image/unit/<卡号>/u_<卡号>_rankup_icon_signed.png`。

### 2.2 `.texb` 格式（已在真实样本上解出）

`.texb` 本身是 honoka v4 加密的 SIF CN 游戏文件，用 `honoka2.exe -b <真实文件名>` 解密后：

```
TEXB | u32 BE 数据区长度 | u16 BE 名称长度 | 名称(路径字符串)
     | u16 ×6：宽 高 ... (0x0080 0x0080 0x008c 0x0004 0x0006 0x0001)
     | TIMG | u16 BE 长度 | u16 BE 名称长度 | 名称(指向同名 .png.imag)
     | 96 字节 IMG 头（含 ffff0001 等标志、宽高、mip 信息）
     | zlib 流 (0x78 0x9c ...)
```

实测验证（`tx_u_normal_icon_11011001.texb`）：

- 头部 `0x0080 0x0080` = **128 × 128**
- zlib 解压后 **恰好 32768 字节 = 128 × 128 × 2**
- 按 **RGB565 小端** 解释可还原出可辨认的卡片图标（已导出 PNG 目视确认）
- 按 RGBA4444 解释画面发灰、明显错误 → 该资源是 **RGB565，无 Alpha**

> 也就是说：一个 texb = 一个 TIMG = 一张 zlib 压缩的 RGB565 位图，暂无 mipmap
> （32768 正好是一级 128×128 的大小）。

### 2.3 导入第三方卡面（已实现为一键工具）

> 2026-10-22 更新：原先"必须重打 APK"的结论**已被推翻**。
> 卡面实体纹理并不在 APK 的 `AppAssets.zip` 里，而在**服务端下发的资源包**
> `static/Android/archives/*.zip`（`assets/image/units/tx_<kind>_<unit_id>.texb`）。
> 所以换卡面既不用 apktool，也不用重签名。

一张卡最多 10 层纹理（实测 unit 41107008）：

| kind | 尺寸 | 用途 |
|---|---|---|
| `u_normal_icon` / `u_rankup_icon` | 128×128 | 部员一览的圆形小图标 |
| `u_*_icon_signed` | 128×128 | 签名卡专用图标 |
| `u_normal_card` / `u_rankup_card` | 256×512 | 卡片立绘 |
| `u_normal_navi` / `u_rankup_navi` | 1024×1024 | NAVI 大图 |
| `b_normal` / `b_rankup` | 512×1024 | 剧情/演出用半身像 |

全部是 **RGB565 + zlib + honoka v4**，同一套流程通吃。

```powershell
cd D:\LLSIFLocal\honoka-chan-dev

# 1) 看这张卡有哪些层（顺带给出每层尺寸）
python tools\cardface.py list --unit 41107008

# 2) 导出原图看一眼
python tools\cardface.py extract --unit 41107008 --kind u_normal_icon --out-dir temp\out

# 3) 三种落地方式，选一种
python tools\cardface.py build  --unit 41107008 --png my.png --out-dir temp\out   # 只生成加密 texb，自检
python tools\cardface.py server --unit 41107008 --png my.png --yes               # 改写服务端资源包（自动备份）
python tools\cardface.py push   --unit 41107008 --png my.png                     # 直推客户端，重启游戏即生效

# 4) 回滚
python tools\cardface.py restore --unit 41107008
```

启动器侧对应「卡池 → 右上角图片图标 / 某张卡的图片按钮」里的
「自定义卡面」对话框：查层 → 用服务端本地路径收料 → 选模式执行，
三种模式与上面三个子命令一一对应。

技术要点（都已在真实资源上验证）：

- **容器逐字节可复现**：`tools/sifcrypt.py` 显式走 v4 两段式初始化
  （先喂头 4 字节、再喂后 12 字节），解密结果与 `honoka2 -b` **完全一致**；
  重新加密时**原样保留原文件 4..16 字节头**，产出的文件与原文件**逐字节相同**
  （之前"重新加密报 version 3"的隐患到此关闭 —— 那 12 字节是资源家族常量：
  APK 内资源是 `c2 09 00 02`，archives 里的纹理是 `c2 26 00 02`，照抄即可）。
- **像素无损**：PNG → RGB565 → 解回 PNG，最大通道差为 0。
- **资源包改写是安全的**：重写后 `zipfile.testzip()` 通过、条目数不变，且
  改前自动备份到 `assets/cardface_backups/<包名>.<时间戳>.bak`。

**已验证：**

| 验证项 | 结果 |
|---|---|
| texb 解密 vs `honoka2 -b` | 4 个真实样本逐字节一致 |
| 重新加密 vs 原文件 | 4 个真实样本**逐字节相同** |
| PNG 往返 | 最大通道差 0 |
| 资源包改写 | 94 条目完好，`testzip` 通过 |
| 回滚 | 恢复后包 md5 与原始完全一致 |
| 服务端 API | 查层 / 收料 / 三种落地模式全部返回 ok |
| 10 层纹理解码 | icon / card / navi / bust 均能解出正确画面 |

**仍需真机确认：**

| 项 | 说明 |
|---|---|
| 客户端缓存 | `push` 的目标是 `files/install/assets/image/units/`；若某台设备该目录没有纹理（全部在包里），要改用 `server` 模式并让客户端重下该包 |
| 生效时机 | 建议清客户端缓存或重启进程后再看 |

**已知风险：**

| 风险 | 说明 | 对策 |
|---|---|---|
| 无 Alpha | RGB565 没有透明通道，异形卡面会带底色 | 背景压成与卡框同色 |
| 尺寸自动缩放 | 不同层尺寸差很多（128² / 256×512 / 1024²） | 用 `list` 先确认尺寸，按目标层单独出图 |
| `server` 模式要重新下载 | 客户端已缓存的包不会自动更新 | 改用 `push` 模式，或清缓存 |
| `AppAssets.zip` 里也有 77 个 texb | 那是 navi 图标等杂物，与卡面无关 | 真要改那批仍需重打 APK（本工具暂不覆盖） |

风险等级：**低**（有备份、可回滚，且完全不碰 APK 签名）。

## 三、还缺什么（能力缺口清单）

`GET /local/admin/overview` 的 `missing` 字段会实时反映这些缺口：

| 缺口 | 现状 | 影响 |
|---|---|---|
| `event_m`（活动主表） | 主数据里没有 | 活动系统（点数/排名/交换所）无法开启，`/event/eventList` 恒返回「无活动」 |
| `user_item`（道具表） | 用户库里没有 | 练习券 / 劝诱券这类道具无处落地，只能发卡和饰品 |
| `user_scenario`（剧情进度） | 用户库里没有 | 只能整表放开剧情，无法做单条控制 |

补齐这三张表之后，管理端对应的按钮会自动亮起（前端就是读 `missing` 决定的）。
