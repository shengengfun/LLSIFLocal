# 管理端 App —— 架构构思、构建方案与变更日志

> 这份文档记录 **Flutter 管理端（`srvapp/`）** 是怎么想出来的、怎么建的、踩过哪些坑，
> 以及每一步的变更记录。服务端接口本身的细节见 [管理端App与服务端修改器.md](./管理端App与服务端修改器.md)。

## 一、总体构思

### 1.1 为什么是「服务端 + 管理端」两层，而不是把服务端塞进 App

一开始考虑过三条路：

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 服务端内嵌 App | 用 gomobile 把 honoka-chan 编成 `.so`/`.aar` 塞进 APK，Android 上直接跑 | ❌ 放弃 |
| B. 服务端独立进程 + App 远程管理 | PC 上跑 `honoka-chan.exe`，App 走 HTTP 管它 | ✅ 采用 |
| C. 纯 Web 管理页 | 服务端自带 `/admin` 网页 | ❌ 放弃 |

放弃 A 的原因很实际：

1. **ANR 与保活**。SIF 客户端要和本地服务端保持长连接式交互，Android 后台进程随时被系统杀，
   一杀游戏就掉线；要保活就得前台服务 + 电池白名单，体验很差。
2. **数据目录**。服务端要读 `assets/main.db`（约 5.8MB）、`assets/data.db`、`1912` 个谱面、
   `static/` 静态资源，这些在 Android 上要么塞 assets（只读）要么首次启动解压几百 MB，
   而 PC 上本来就有一份完整的。
3. **调试成本**。Go 交叉编译到 Android 的 sqlite 驱动（`modernc.org/sqlite`）是纯 Go 实现，
   能用，但一旦出问题日志很难看；而 B 方案下服务端日志可以直接在 PC 终端看。

所以定下来的形态是：**PC 上跑服务端，App 负责把它拉起来、盯着它、改它的配置**。

> 注意区分两件事：「服务端进程在哪跑」和「谁负责启动它」。
> **启动/终止服务端是 App 的第一职责**（不是"可选的高级功能"）：
> - 打开 App 时如果连不上，且本机能跑服务端，**自动拉起** `honoka-chan.exe`（默认开启，可在总览页关掉）；
> - 总览页第一张卡就是「启动服务 / 终止服务 / 重启」，是真子进程 + 真端口探测；
> - 只有 Android 端因为**它是个 Android 设备，跑不了 Windows 的 exe** 而无法启动本机服务端，
>   这种平台上界面会明确说明原因，并自动降级为「连局域网里的 PC 服务端」。
>   这是平台能力边界，不是设计上"不想做"。

> 这也带来一个明确的设计约束：**App 的所有能力必须落在服务端的 `/local/*` 接口上**，
> App 自己不做"只有 App 能做"的事。这样 Web 端、curl、脚本都能复用同一套接口，
> 出问题时也能用 curl 复现（本项目的验证几乎全靠 curl）。

### 1.2 为什么一个 Flutter 工程同时出 Windows 和 Android

用户要求「Windows/Android 一次搞定，共用 UI 省维护成本」，Linux 暂不考虑。落地方式：

- 一套 `lib/`，UI 完全共用；
- 平台差异收在 3 个点，且都有运行时降级：
 1. `ServerProcess`：只有桌面端能 `Process.start` 拉起 `honoka-chan.exe`；
    Android 上 `supported == false`，界面自动禁用「启动/终止」并说明原因（仍可通过
    `POST /local/admin/shutdown` 停掉远端服务端）。
 2. `guessServerPaths()`：桌面端从「当前目录 / 可执行文件目录」逐级向上找
    `honoka-chan-dev/honoka-chan.exe`；Android 直接返回 `null`，让用户手填。
 3. 布局：宽度 ≥ 760 用 `NavigationRail`（桌面/平板），否则用底部 `NavigationBar`（手机）。

### 1.3 分层

```
┌──────────────────────────── Flutter (srvapp/) ────────────────────────────┐
│  pages/           页面（总览 / 账号 / 玩家详情 / 卡池 / 乐曲 / 工具）        │
│  widgets.dart     共用小组件（ErrorView / EmptyView / NumberField / showSnack）│
│  theme.dart       设计令牌（AppColors / AppRadius / buildTheme / AppBackdrop）│
│  state.dart       AppState：连接配置 + 主题 + 服务进程 + 运行态（ChangeNotifier）│
│  api.dart         LocalApi：/local/* 的薄封装，纯 JSON → 模型                 │
│  models.dart      数据模型（Overview / Player / UnitItem / LiveItem / MailBoxItem…）│
│  server_control.dart  ServerInfo / LogLine / ServerProcess / 本机 IP 探测      │
└───────────────────────────────────┬───────────────────────────────────────┘
                                    │ HTTP /local/*
┌───────────────────────────────────▼───────────────────────────────────────┐
│ honoka-chan (Go)                                                          │
│  internal/handler/local/   管理端接口（accounts / admin/* / switch / unbind）│
│  internal/handler/reward/  游戏内礼物箱（rewardList / rewardOpen）           │
│  internal/mailbox/         user_present_box 存储（管理端与游戏内共用）        │
│  internal/useritem/        user_item_data 存储                             │
│  internal/logbuf/          环形日志缓冲（给管理端看）                        │
│  internal/schema/local/    管理端接口的请求/响应结构                         │
│  config/root.go            数据根目录探测（CWD 去依赖）                      │
└───────────────────────────────────────────────────────────────────────────┘
```

**为什么不用 Provider / Riverpod / Bloc？**
这个 App 的共享状态只有一份（连接参数 + 主题 + 服务进程 + 运行态），
用一个 `ChangeNotifier` + `AnimatedBuilder` 就够；多引一个 DI 框架只会让
「服务进程」这种有副作用的对象更难推理。页面内部状态（分页、筛选）留在各自
`State` 里，不上升。

**为什么要 `LocalApi` 做薄封装而不是在页面里直接 `http.get`？**
两个原因：一是测试要能注入 `MockClient`（见 4.2）；二是 `_ok()` 统一把
`{"ok":false,"message":...}` 转成 `ApiException`，避免每个页面各写一遍错误处理。

## 二、关键设计决策（ADR 风格）

每条都记下「当时怎么想的 / 为什么不用另一种 / 代价是什么」。

### ADR-00 启动 / 终止服务端是 App 的第一职责，不是附加功能

- **背景**：早期文档里我用过「App 只是遥控器」这种说法，容易被理解成"启动服务端要靠用户自己去双击 exe"。
  实际实现从一开始就是 App 自己 `Process.start` 拉起服务端，但**默认没有在启动时自动拉**。
- **结论**：这件事必须是第一职责，权重高于任何修改器功能。落地成三条：
 1. `AppState.load()` 末尾：先 `_autoConnect()`（2 秒超时静默探测）→ 仍连不上就 `startServer()`，
    默认**打开 App 即自动启动服务端**；开关是总览页的「打开 App 时自动拉起服务端」，状态存 `srv_autostart`。
 2. 总览页在**未连接**状态下，第一颗按钮就是「启动服务端」（桌面端），旁边才是「重试连接」；
    并把自动启动失败的原因（找不到 exe / 启动后立即退出 / 25 秒超时）原样显示出来。
 3. 可执行文件路径支持自动探测（从 CWD 和 exe 目录各向上找 8 层，找 `honoka-chan-dev/honoka-chan.exe`），
    也允许手动填。
- **实测**：先杀掉服务端 → 8080 确认关闭 → 只启动 App → **第 4 秒** `honoka-chan` 进程出现（pid 17928，
  是 App 的子进程），`/local/ping` 返回 `user_count=4`，`/local/admin/server` 返回 `uptime_sec=4`。
- **Android 的平台边界**：`honoka-chan.exe` 是 Windows PE，Android 跑不了，
  所以 `ServerProcess.supported == false`，界面禁用启动按钮并写明原因。
  想真的在 Android 上跑服务端，需要把 Go 服务端交叉编译成 Android 原生（gomobile / 纯 Go + sqlite），
  那是另一个量级的工程，且要处理前台服务保活、几百 MB 资源解压等问题 —— 目前不做，但不排除。
- **代价**：自动启动会让"只想看看界面"的用户也拉起一个进程；所以给了开关，并让它失败时**只提示不阻塞**。

### ADR-01 服务端数据路径全部走 `config.Root`，不依赖 CWD

- **背景**：App 用 `Process.start` 拉起 `honoka-chan.exe` 时可以指定
  `workingDirectory`，但如果用户手动双击 exe、或者放计划任务里跑，CWD 就不对了。
- **症状**：在别的目录启动时 `assets/main.db` 打不开直接 panic；
  `hasBeatmap()` 用相对路径 `assets/serverdata/beatmaps`，所有曲子会从列表里"消失"。
- **做法**：`config.Root` 在包初始化时确定根目录，判定依据是「同时存在 `assets/` 与 `static/`」，
  探测顺序是 CWD → exe 目录向上 → 源码目录向上。`db.locateDbFile` 统一返回**绝对路径**。
- **代价**：包初始化期间做了一次磁盘探测（几十微秒），换来的是"从哪启动都对"。

### ADR-02 端口是否被占用：先 Dial，再比对 pid

- **踩的坑**：第一版用 `net.Listen` 探测端口空闲，Windows 上**被占用时仍然 bind 成功** ——
  因为 Windows 默认不设 `SO_EXCLUSIVEADDRUSE`，允许重复 bind。于是"改端口到 8080"
  明明是自己占着，却被判为"空闲"，写进 config 后重启直接起不来。
- **做法**：`DialTimeout` 试探 → 连得上就 `GET /local/admin/server` 拿 `pid` →
  `pid == os.Getpid()` 才算"本进程占着"，否则如实报"被其他程序占用"。
- **代价**：探测多一次 HTTP 往返（本机 ~1ms）。

### ADR-03 日志用环形缓冲 + 增量拉取，而不是 WebSocket

- **背景**：总览页要显示服务端终端输出。
- **候选**：WebSocket / SSE / 长轮询 / 客户端定时拉。
- **选择**：服务端 `internal/logbuf`（4000 行环形缓冲，带自增 `seq`），
  客户端每 2 秒 `GET /local/admin/logs?after=<seq>&limit=`。
- **理由**：WebSocket 要在 App 里维护重连状态机，而且 Android 上切后台会断；
  环形缓冲 + `seq` 增量的实现只有 100 行，断线重连天然正确（`after` 传上次的 `next` 即可），
  也不会因为客户端卡顿把服务端拖死。
- **代价**：最坏 2 秒延迟；环形缓冲满了会丢最老的日志（4000 行足够看一次启动过程）。

### ADR-04 日志来源要 tee 两路

`log` 包和 `gin` 的访问日志是两个输出源。只 tee 一路的话，总览页要么看不到
「服务端启动完成」，要么看不到「谁在请求哪个接口」——而排查问题时恰恰两样都要。
做法：`log.SetOutput(io.MultiWriter(os.Stderr, logbuf.Writer{}))`，
`gin.DefaultWriter` / `gin.DefaultErrorWriter` 同样 tee。

### ADR-05 乐曲"上线/下线"不改主数据表，而是搬谱面文件

- **发现**：`internal/handler/api/live/common.go` 里 `listAvailableNormalLiveRows()`
  最后一句是 `if !hasBeatmap(row.NotesSettingAsset) { continue }`。
  **曲子能不能玩，只看谱面文件在不在 `assets/serverdata/beatmaps/`**。
- **做法**：下线 = 把谱面移到 `assets/serverdata/beatmaps_disabled/`，上线 = 移回来。
- **为什么好**：① 不用改表结构，不用碰 `normal_live_m` / `special_live_m`；
  ② 完全可逆，文件不删；③ 活动曲（`special_live_m`）走同一套机制，顺带就把
  "控制哪些曲子在线"做完了；④ 和"谱面导入"天然一体 —— 导入一个谱面就等于上线一首曲子。
- **代价**：语义上"上线"依赖文件系统，跨机器同步时必须连 `beatmaps_disabled/` 一起同步。

### ADR-06 礼物箱放在独立 `internal/mailbox` 包

管理端（`internal/handler/local`）要发件，游戏内接口（`internal/handler/reward`）要
列表和领取。如果让 `reward` import `local`，包的依赖方向就乱了（游戏内逻辑依赖管理端）。
所以把「表 + 增删查」抽成 `internal/mailbox`，两边都只依赖它。

### ADR-07 道具用「静态基础表 + 玩家增量」而不是重写

原版 `/item/itemList` 是读静态 `assets/serverdata/item_data.json`，所有人同一份
（每样 999）。如果直接改成读表，老存档会"道具全空"。
做法：静态表照读，再把 `user_item_data` 里该玩家的增量叠加/追加进去 ——
老行为不变，新发的道具能出现。

### ADR-08 自定义卡面：宁可保留手动一步，也不做"假装成功"

客户端读的是**加密后的 `.texb`**（`TEXB` 容器 + 96 字节 IMG 头 + zlib + honoka 加密）。
App 侧做 PNG → texb 的编码器技术上可行（Go 有 `image/png` 和 `compress/zlib`），
但 96 字节 IMG 头的字段语义和 honoka v4 加密目前只能靠现成工具产出，
自己写一遍极可能做出「生成成功、进游戏白图」的结果。
所以 App 只做**收料 + 归档 + 一键复制转换命令**，把最后一步留给 `tools/texb.py` + `honoka2`。
**这是权衡，不是偷懒**：宁可少一个按钮，不要多一个"看起来能用实际白图"的按钮。

### ADR-09 主题令牌照抄参考项目，而不是自己调色

用户明确说"颜色太丑"，并给了参考项目 `D:\Project\LanzhuToolNX`。
直接把 `tauri-ui/src/globals.css` 的 CSS 变量搬成 `AppColors` 的两套常量
（浅色 / 深色），`buildTheme()` 映射到 `ColorScheme`，`AppBackdrop` 复刻
「左上蓝光 + 右上紫光 + 竖向渐变」。
好处是**以后想调色只改一处**；坏处是 Flutter 没有 CSS 变量，深浅色切换要整棵树重建
（`AnimatedBuilder` 包着 `MaterialApp`，实测无感）。

### ADR-10 轮询页面不能用 `pumpAndSettle`

总览页有 2 秒定时器，`await tester.pumpAndSettle()` 会一直等下去直到超时。
测试里改成 `pump()` + `pump(Duration(milliseconds: 50))`，
并在用例结束前 `pumpWidget(SizedBox())` 卸载页面，让 `dispose()` 取消 `Timer.periodic`。

### ADR-11 App 开着就必须保证服务端活着（看门狗）

- **背景**：实际使用中出现过「App 明明开着，客户端却一直网络请求超时」——
  原因是服务端进程已经没了（手动杀、崩溃、被别的清理工具收掉），而 App 只是显示"连不上"，
  不会自己动手。用户视角就是"App 开着怎么还连不上"。
- **做法**：`AppState` 起一个 5 秒周期的看门狗：
 1. `_ping()` 通 → 清空失败计数，状态回到「运行中」；
 2. 不通 → 连续 **2 次**（约 10 秒，避免瞬断误判）后：若进程还在先 `stop()`，再 `startServer()`；
 3. 用户主动点「终止服务」会置 `_userStopped = true`，看门狗不再自作主张；
    再点「启动服务」或「重启」时清掉这个标记。
- **实测**：App 运行中直接 `Stop-Process honoka-chan`（模拟崩溃）→ **第 15 秒**服务端被拉回来；
  另一次测「换新 exe 后崩溃恢复」→ **第 5 秒**恢复，并且用的是新编出来的二进制。
- **代价**：每 5 秒一次本机 HTTP 探测（~0.5ms），可以忽略；崩溃恢复期间客户端会有十几秒空窗。

### ADR-12 「新号从零开始」做成开关，而不是删掉满配逻辑

- **背景**：原版 honoka-chan 建号时把 `common_unit_data` 全表 3963 张卡一次性塞给新号，
  再加等级 1028 / 金币 1.1 亿 / LP 417 / 全部饰品 —— 等于把养成全跳过。
  用户希望重建原版游玩逻辑，从零开始，道具和卡由管理端发。
- **做法**：`config.json` 增加 `new_user_vanilla`（指针类型，缺省视为 `true`）与 `initial_unit_id`（默认 31）。
  - 原版模式：只插入 1 张初始卡，卡组里只放这 1 张，`user_pref` 用 等级 1 / LP 25 / 金币 0 / NextExp 30，不给饰品。
  - 满配模式：保持旧行为。
- **连带修的坑**：`UserPref.ApplyProfileDefaults()` 原来会把 `exp == 0`、`coin == 0` 当成"数据缺失"
  直接补成 1089696 / 112124104 —— 也就是说原版新号的 0 金币会被悄悄改回 1.1 亿。
  现在改成只在 `< 0` 时兜底，数值来源统一走 `NewUserStats()`。
- **实测**：`go run ./cmd/newusercheck 13900000001` →
  `created=true`，`{UserLevel:1 GameCoin:0 SnsCoin:0 EnergyMax:25 NextExp:30}`，
  `units=1 accessories=0 deck_units=1`。测完把测试账号的行全部删掉（`users` 仍是原来 4 个）。
- **代价**：已有账号不会自动变回"从零"，要重置只能手动改库（文档给了备份与还原方式）。

### ADR-13 乐曲解锁状态按官方数据还原，可回滚

- **背景**：之前为了验证修改器，`POST /local/admin/unlock` 把 `normal_live_m.default_unlocked_flag`
  全置成 1（972/972 全解锁），这不是原版状态。
- **做法**：`tools/restore_live_unlock.py` 从抓包留存的完整主数据 `zhuabao/zhuabao/tmp.db`
  读回原始 flag（992 条里只有 **36** 条默认解锁），先备份 `main.db` 再逐条改。
- **实测**：`改动 936 条；现在的分布：[(0, 936), (1, 36)]`，`/local/admin/overview` 显示 `live_unlocked=36/972`。
- **回滚**：备份在同目录 `assets/main.db.bak<时间戳>`，直接覆盖回去即可。

### 2026-10-22 · 回合 9：抽卡必崩 + 重启后全员「维护中」

### B. LP 从「假满」改成真数据

原来 `userInfo.current_energy` 恒等于上限（等于无限耐力）。现在：

- `user_pref.energy_update_time` 记录最后一次扣 LP 的时间，`EffectiveCurrentEnergy()`

### C. `energy_full_time` / `energy_full_need_time` 原来是假的

`session/userdata.go` 和 `handler/live/play.go` 里这两个字段原来写死成：

```
energy_full_time      = "2023-03-20 01:28:55"   // 早就过去的时间
energy_full_need_time = 0                        // LP 没满却是 0
```

LP 一直是满的时候客户端根本不走倒计时分支，所以看不出问题；一旦 LP 真实（比如 5/39），
客户端要按这两个字段算「下一点 LP 什么时候回来」，就会踩到自相矛盾的数据。

现在改成现算：

- `UserPref.EnergyFullNeedTime() = (上限 - 当前) * 360`
- `UserPref.EnergyFullTime() = now + need_time`，格式 `2006-01-02 15:04:05`

### D. `social_point` 是 NULL 导致「友情点加不上去」

`social_point` 是后加的列，SQLite 给老行补的是 **NULL**。Go 侧 Scan 成 0 看不出异常，
但 SQL 的 `social_point = social_point + 10` 结果还是 NULL，等于友情点永远加不上。

- `startup.BackfillUserPrefColumns()` 启动时把 `social_point`、`over_max_energy`、
  `user_exp`、`energy_update_time` 的 NULL 统一刷成 0。
- `autoplay.playOnce` 的 UPDATE 改成 `COALESCE(social_point, 0) + ?` 兜底。

### E. Live 界面闪退：定位手段与结论

**症状**：进 Live 相关界面后进程直接消失，没有弹窗、没有崩溃提示。

**排查过程**（这套方法以后还能用）：

1. 闪退后拉 tombstone：`su -c 'cat /data/tombstones/tombstone_XX'`
   → `signal 5 (SIGTRAP) ... #00 pc 0x259a2c libGame.so`，
   调用栈是 `GLES20GameRenderer.onDrawFrame → JNI → libGame.so`。
2. 把 `libGame.so` 拉回 PC，用 `pyelftools + capstone` 反汇编崩溃地址附近：
   - `0x259a2c` 是 `brk #1`，前面是 `mov w0,#4 / adrp+add x1,"%s" / mov x2,buf / bl syslog`。
   - 结合 `cmp w21,#2/#4/#6` 分别取 `"runtime error: %s (%s)"`、
     `"memory allocation error: %s (%s)"`、`"error in error: %s (%s)"`，
     可以确定这是 **Lua 的 pcall 状态码**分支 —— 也就是说
     **客户端 Lua 抛了一个没人接的错，panic 路径把进程 brk 掉了。**
3. `syslog()` 在 Android 上走 bionic 的 `vsyslog` → `async_safe_format_log`，
   也就是 **会进 logcat**，tag 是 `getprogname()`（这里是 `app_process64`）。
   而且非 ASCII 的消息会被 logcat 用 **base64** 打出来，要自己解：

   ```powershell
   adb shell "logcat -d -b all -v time -T '10-22 12:50:20.000'"
   # 找到 tag=app_process64、内容是 base64 的那行，丢进 base64 -d
   ```

   解出来是：

   ```
   runtime error: ?:0: attempt to index a nil value
   stack traceback:
       ?: in function '?'
       ?: in function 'initialize'
       ?: in function 'create'
       ?: in function 'createForm'
       ?: in function <?:20> (setup)
   ```

**结论**：某个界面的 `setup → createForm → create → initialize` 里索引了一个 nil。
客户端 Lua 是加密 + 去符号的（chunk 名/行号都是 `?`），拿不到具体文件行号，
只能靠「改服务端数据看崩不崩」二分定位。

**关键坑**：`setprop wrap.<package> logwrapper` 想抓 stderr 是 **无效且有害** 的
（进程 cmdline 没有变化，等于没生效，反而让客户端卡在 `/v1/*` 握手阶段一直重试）。
排查完记得 `setprop wrap.klb.android.lovelivecn ''` 清掉。

**已排除的点**：

- `/main.php/api` 批处理的 29 个子请求全部有返回，没有 `null`
  （`handler/api/api.go` 里加了「返回空结果」告警；把 `debugAPIBatch` 改成 true
  可以打印每个子模块名，排查界面数据来源很方便）。
- `/live/partyList` 响应里没有 null 字段，LP 相关字段已自洽。

**下一步**：需要一次「进入 Live 的复现」，同时开 logcat 抓 base64 消息；
拿到新的 stack traceback 后按「哪个界面 → 哪个 setup」继续二分。

## 回合 12：Live 闪退的真正原因 —— 队伍只有 1 个人

### A. 先搞清楚客户端 Lua 是可以读的（重大工具突破）

`install/` 下的 `.lua` 是「SIF CN v4 加密 + Lua 5.1 字节码（版本字节被改成 0x52 反调试）」，
`honoka2.exe -b <文件名> <in> <out>` **能全部解开**（文件名必须和原文件一致，解密依赖文件名）：

```powershell
# 1. 把设备上的 Lua 全拉到 PC
adb pull /data/data/klb.android.lovelivecn/files/install/luatree
```

这就是本轮能定位问题的关键（`temp/luadec/` 里现在是全部 1979 个 Lua 的明文）。

### B. 抓 Lua 报错的方法（重要，以后直接用）

闪退是「Lua 抛错 → panic 路径 brk 掉进程」，所以**没有任何弹窗**。
但 Lua 的错误字符串会经 `syslog` → bionic `async_safe_format_log` 落到 logcat，
tag 是 `app_process64`，**非 ASCII 内容会被 base64 编码**：

```powershell
adb shell "logcat -d -v time -T '10-22 13:59:00.000' > /sdcard/w.txt"
# 找 tag=app_process64、内容像 base64 的行，解出来就是：
#   runtime error: ?:0: attempt to index a nil value
#   stack traceback:
#       ?: in function '?'
#       ?: in function 'initialize'
#       ?: in function 'create'
#       ?: in function 'createForm'
#       ?: in function <?:20> (setup)
```

黑坑：`setprop wrap.<package> logwrapper` 想抓 stderr **无效**（cmdline 没变），
还会让客户端卡在 `/v1/*` 握手反复重试。用完记得 `setprop wrap.klb.android.lovelivecn ''` 清掉。

### C. 用 `<?:20>` 反查是哪个界面

客户端 Lua 是 `luac -s` 编译的（strip 掉了 chunk 名和行号），所以栈里全是 `?`，
**但 `lineDefined` 保住了**：`<?:20>` 表示「这个函数定义在第 20 行」。

写了个扫描器：对每个含 `createForm` 的 Lua，定位主 chunk 的常量表，
再读第一个子函数的 `linedefined`，筛出 18~22 的：

```
ld=19  m_exchange/view/elements/select.lua
ld=19  m_ranking/score_detail/start.lua
ld=20  m_live_menu/select_deck_menu.lua      <== 命中
ld=21  m_live_menu/select_friend_menu.lua
```

`select_deck_menu.lua` 的 `setup` 正好定义在第 20 行 → **闪退的是「选择队伍」界面**，
不是之前以为的「选择好友」界面。

### D. 真正的原因：队伍只有 1 个成员

`m_live_menu/select_deck_menu.lua` 的 `setup → createForm → create → initialize`
里固定遍历 9 个队伍位置，少一个就索引 nil。而数据库里：

```

  deck 1  (user 377385143) → 9 条，position 1..9   ✅
  deck 18 (user 1792630206) → 1 条，position 1     ❌  ← 崩的就是这里
```

根因在 `internal/accountreg/accountreg.go` 的「原版从零」分支：
建号只发 1 张初始卡，队伍里也只放这 1 张。
SIF 的教学关本来是给一支**满编 9 人**队伍的。

   并顺带修正 `user_pref.unit_owning_user_id` 指向自己主队里的卡。
2. **`internal/accountreg/accountreg.go`**：`starterUnitIDs()` 发 9 张初始卡
   （`unit_id 1..9` 正好是 9 张 N 卡，即教学关那 9 个人），
   建队时把这 9 张按 position 1..9 填进去。
3. **`internal/schema/live/partylist.go`**：`PartyList` 同时发 `friend_status`（单数，
   客户端实际读的就是这个）和 `friend_statuses`（保留兼容）。
4. **`internal/session/userdata.go`**：新增 `BuildUserInfo(userID, pref)`，
   嘉宾的 `user_info` 用他自己的档案（原来是拷自己的数据只改 user_id，
   LP / 金币 / 友情点全是自己的）。

**实测**：

### C. 客户端怎么触发（`temp/gm/src/com/sifpatch/AutoPlay.java`，新增）

- 取 `/local/gm/chart` → 拿 `notes` + `elapsed_ms` + `live_started`；

- 已经过去的音符直接跳过，避免一开就补打一堆堆积键。

### D. 轨道坐标：改成一键校准

判定区是**弧形**的（`m_live/settings.lua` 里有 `calcThetaByPosition` /

9 轨的几何参数在**加密的二进制 UI 树**里（`ui_live.json` 解密后是节点树二进制，

改成 SIF 自己调整工具的思路：**点一次校准**。

节奏对不齐时用面板上的「偏移 ±20ms」微调（存 `ap_offset_ms`）。

## 回合 14：自定义卡面（不重打 APK 就能换图）

### A. 先纠正一个前提

上一版调研认为卡面在 APK 的 `AppAssets.zip` 里，所以要 apktool + 重签名。
实测推翻：`AppAssets.zip` 里只有 77 个 texb（navi 之类），**卡面实体纹理在服务端下发的资源包**
`static/Android/archives/*.zip`，路径是 `assets/image/units/tx_<kind>_<unit_id>.texb`。

| kind | 尺寸 | 用途 |
|---|---|---|

### B. 打通 honoka v4 加解密（关键突破）

`honokamiku_decrypt_init` 之后还有一个独立的两段式初始化，之前一直漏调：

```
decrypt_init(ctx, mode, gamefile_id, prefix, filename, 头 4 字节)
decrypt_final_init(ctx, gamefile_id, key_tables, name_sum, filename, 后 12 字节)
```

- 新增 **`tools/sifcrypt.py`**：加解密都走 libhonoka，模块与命令行两用

## 回合 15：Android 设备开服

### A. 问题

之前启动器在 Android 上只能「连 PC 的服务端」：`ServerProcess.supported` 直接
`Platform.isWindows || isLinux || isMacOS`，因为 PC 版 `honoka-chan.exe` 在手机上跑不了。

### B. 关键技术障碍：Android 不让随便执行文件

三条限制叠在一起：

1. **Android 10+ 禁止执行 app 可写目录里的文件**（`app_data_file` 的 `execve` 直接 EACCES）
   → 不能把二进制拷到 `files/` 再 exec。
2. **必须是 PIE**：`GOOS=linux` 编出来是 `ET_EXEC`，Android 5+ 报
   "only position independent executables (PIE) are supported"。
3. **PT_INTERP 必须是 `/system/bin/linker64`**：`GOOS=linux` 写的是
   `/lib/ld-linux-aarch64.so.1`，Android 上没这个路径，`execve` 直接 ENOENT。

### C. 解法：`GOOS=android` + native lib 目录

- `GOOS=android GOARCH=arm64 CGO_ENABLED=0 go build` —— honoka-chan 是纯 Go
  （SQLite 用 `modernc.org/sqlite`），**不需要 NDK**，直接产出
  `ET_DYN`(PIE) + `PT_INTERP=/system/bin/linker64` 的 Android 可执行文件
- 把它当成 native lib 打包：`android/app/src/main/jniLibs/arm64-v8a/libhonoka_chan.so`
  —— APK 的 `lib/` 目录属于 `apk_data_file`，**允许执行**
- Gradle 侧必须加：
  ```kotlin
  packaging { jniLibs {
      useLegacyPackaging = true                       // 解压成真实文件
      keepDebugSymbols += "**/libhonoka_chan.so"      // 别被 strip 削坏
  } }
  ```
  加上 `AndroidManifest` 的 `android:extractNativeLibs="true"`
- 新增 `tool/build_android_server.ps1`：交叉编译 + **自检 ELF**
  （machine=183、`e_type=3`、`interp=/system/bin/linker64`），不满足直接报错

### D. 数据目录与启动

- 服务端新增 `HC_ROOT` 环境变量（`config/root.go`）：Android 上服务端装在
  `/data/app/.../lib/`，靠「exe 所在目录」推不出数据在哪，由启动器显式传
- 数据根目录：`/storage/emulated/0/Android/data/com.llsiflocal.llsif_local_admin/files/srv`
  —— app 私有外部目录，**免存储权限**、USB 直接可见、卸载即清
- 启动器 `server_control.dart`：
  - `androidNativeLibDir()` 从 `/proc/self/maps` 里找 `libflutter.so`/`libapp.so`
    的路径，反推 lib 目录（不需要平台通道）
  - `androidServerRoot()` 在候选目录里挑**已经有 assets/ 与 static/** 的那个
  - `inspectServerRoot()` 体检：assets / static / `static/Android/archives` 里的 zip 数量
  - `bootstrapAndroidRoot()` 首次建目录骨架 + 写默认 `config.json`
  - `start()` 在 Android 上带 `environment: {'HC_ROOT': workDir}`，
    并把「缺 assets/static」「缺资源包」写进启动日志
- 总览页：Android 不再显示「本平台不支持」，改成显示数据目录、缺什么、资源包数量，
  带「初始化数据目录 / 重新检查」按钮

### E. 清单与权限

- `AndroidManifest` 补 `INTERNET`（Flutter release 默认不带，不加连 127.0.0.1 都失败）、
  `ACCESS_NETWORK_STATE`、`usesCleartextTraffic="true"`
- 出包后核对：`aapt2 dump xmltree` 确认 `extractNativeLibs=true`；
  `libhonoka_chan.so` 在 APK 里 `method=8`（deflate）且与源文件逐字节一致

### F. 验证状态

- 交叉编译自检通过：`PIE + /system/bin/linker64`，25.1 MB
- APK 32.1 MB，`lib/arm64-v8a/libhonoka_chan.so` 存在、`extractNativeLibs=true`、
  `INTERNET` 权限已声明；`flutter analyze` 无告警
- Windows 启动器同步重建并冒烟通过（回归没坏）
- `HC_ROOT` 实测：用环境变量指向 `honoka-chan-dev` 起第二个进程，能正常读库并加载
  3644 张卡白名单
- **仍未做**：真机跑一次。设备没连，`execve` 那步（SELinux 会不会放行）和
  `/proc/self/maps` 反推 lib 目录都需要上机确认

### G. 已知限制

- 只编了 `arm64-v8a`；`armeabi-v7a` 要跑
  `tool/build_android_server.ps1 -Abis armeabi-v7a`（脚本已支持），否则老 32 位机
  上「启动服务端」会提示缺少 lib
- 服务端跟 App 同生命周期：App 被系统杀掉服务端一起没，靠 5 秒看门狗在 App 活着时拉起。
  要做成「长期后台开服」得加前台 Service + 常驻通知（未做）
- 手机上要放 15 GB 资源；同机玩还要再算客户端自己那份缓存
