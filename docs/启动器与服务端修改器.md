### 修改器语义要点

- **属性修改**只写 patch 里出现的字段（`ProfilePatch` 全指针），避免误改其它属性；
  写完会置 `force_relogin=1` 并 `profile_version+1`，客户端需重新登录才刷新。
- **发卡**写 `user_unit_data`，`display_rank` 取该卡的 `rank_max`；
  已拥有的会跳过并计入 `skipped`。
- **发饰品**写 `user_accessory`，同一 `accessory_id` 允许多份。
- **解锁乐曲**改的是主数据 `normal_live_m.default_unlocked_flag`，
  对**所有账号**生效，属于全局修改器操作。

### 能力缺口

`/local/admin/overview` 返回 `missing` 数组，前端据此把对应功能标为不可用：

| 值 | 含义 | 原因 |
|---|---|---|

| `item` | 道具发放不可用 | 用户库缺 `user_item` |
| `scenario_progress` | 剧情单条控制不可用 | 用户库缺 `user_scenario` |

## 八、服务控制 / 终端输出 / 网络端口（本轮新增，全部实测）

### 8.1 新增接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/local/admin/server` | pid / 运行时长 / 根目录 / exe / go 版本 / 监听端口 / cdn_server / 局域网 IP / 账号数 |
| GET | `/local/admin/logs?after=&limit=` | 服务端环形日志，`after` 传上次的 `next` 做增量 |
| POST | `/local/admin/config` | 改 `listen_port` / `cdn_server`，返回 `restart_required` |
| POST | `/local/admin/shutdown` | 优雅退出（响应发出后 200ms 退出进程） |

日志来源是 `internal/logbuf`（4000 行环形缓冲），`main.go` 把 `log` 和
`gin.DefaultWriter/DefaultErrorWriter` 都 tee 进去，所以**标准库日志和 gin 访问日志都能在 App 里看到**。

### 8.2 端口探测的坑（Windows 特有）

第一版用 `net.Listen` 探测端口是否空闲，结果被占用时仍然"空闲"——
Windows 默认不设 `SO_EXCLUSIVEADDRUSE`，允许重复 bind。
改成：**先 Dial 连接**，连上了再 `GET /local/admin/server` 比对 `pid`，
pid 是自己才算"本进程占着"，否则如实报占用。

## 九、乐曲上线 / 谱面导入导出 / 卡面库 / 礼物箱（本轮新增）

### 9.1 关键发现：乐曲"能不能玩"只看谱面文件在不在

`internal/handler/api/live/common.go` 的 `listAvailableNormalLiveRows` 末尾有一句
`if !hasBeatmap(row.NotesSettingAsset) { continue }` —— 谱面文件不存在，这首曲子
直接不出现在列表里。于是「上线 / 下线」不需要改任何主数据表：

- 下线 = `assets/serverdata/beatmaps/<file>` → 移到 `assets/serverdata/beatmaps_disabled/`
- 上线 = 移回来

随时可反悔，也不会破坏主数据。`special_live_m`（活动曲）走同一套机制。

> 顺带修了一个隐患：`hasBeatmap` 原来用的是 CWD 相对路径，从别的工作目录启动时
> 所有曲子都会"消失"。现在统一走 `config.Path`。

### 账号增删（本轮新增）

- **新建**：管理端「账号 → 新建账号」填手机号/密码/昵称即可，内部复用建号逻辑
  （`internal/accountreg`，从 `ghome/account` 抽出来以解开 import 环），因此

### 9.3 礼物箱（邮箱）打通了什么

原版服务端 `reward/rewardList` 是**硬编码返回空列表**，`rewardOpen` 根本没注册，
`topInfo.present_cnt` 恒为 0 —— 也就是礼物箱整个是死的。现在：

- `internal/mailbox`：`user_present_box` 表（present_box_id / user_id / add_type /
  item_id / amount / item_category_id / subject / insert_date / opened），管理端与
  游戏内接口共用，避免互相 import。
- `reward/rewardList` 返回真实未领取邮件（奖励对象字段沿用客户端已在解析的
  `Rewards` 结构，与战斗结算同一套）。
- `reward/rewardOpen`（新增注册）领取：`add_type=1000`（部员）写 `user_unit_data`，
  其余写 `user_item_data`，并把 `item_list` / `unit_list` 回给客户端做本地增量。
- `topInfo.present_cnt` 改为真实未领取数。

### 9.4 道具落地

原版服务端没有道具表，`/item/itemList` 是读静态 `assets/serverdata/item_data.json`
（给所有人同一份）。现在改成：**静态表 + `user_item_data` 增量**（`internal/useritem`），

### 9.5 卡面库的边界（重要）

客户端读的是**加密后的 `.texb`**，服务端做的只是 PNG 收料与归档：

1. App 里「工具 → 自定义卡面库」扫描 `static/custom/cardart/`，可直接删、可复制目录
2. 出料要走两步（App 提供一键复制命令）：
   `python tools/texb.py encode --png <PNG> --template <原版.texb> --out <out.texb>`
   再 `honoka2.exe -e -c <out.texb>` 加密
3. 加密后的 texb 放回客户端对应资源位（详见 `第三方卡面与谱面导入调研.md`）

之所以不假装一条龙：texb 的 96 字节 IMG 头与 honoka v4 加密目前只能靠现成工具产出，
App 里硬做一遍反而容易做出"看起来成功、进游戏白图"的结果。

### 9.7 活动系统现状（说清边界）
